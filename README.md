# ИДЗ №2 АКОС — вариант 32 «Кухня ресторана»

Консольное приложение на C11 для Linux, моделирующее работу кухни ресторана
с помощью **реальных POSIX-потоков (`pthread`)**.

В отличие от ИДЗ №1, где события моделировались последовательно, во второй
работе участники ресторана выполняются асинхронно и синхронизируются
мьютексами и семафорами.

## Что реализовано

- отдельный поток для каждого посетителя;
- отдельный поток для каждого официанта;
- отдельный поток для каждого повара;
- отдельный поток координатора кухни;
- блюда как последовательности зависимых операций;
- оборудование четырех типов: `stove`, `oven`, `grill`, `table`;
- считающие семафоры для оборудования;
- ограниченная кухонная очередь;
- ограниченная зона готовых блюд;
- правила приоритета `FIFO` и `LIFO`;
- явные и автоматически формируемые заказы;
- воспроизводимый `seed` для случайных заказов;
- подробный событийный вывод;
- потокобезопасное логирование через `open` / `write` / `close`;
- обработка `SIGINT` и `SIGTERM`;
- корректное завершение всех потоков через `pthread_join`;
- итоговая статистика;
- автоматические тесты;
- отдельные проверки ASan/UBSan и ThreadSanitizer.

## Потоки модели

### Посетители

На каждого посетителя создается свой `pthread`.

Поток посетителя:

1. ожидает времени прихода;
2. сообщает о появлении;
3. формирует/публикует свой заказ;
4. сигнализирует о необходимости официанта;
5. ожидает выдачи или отмены заказа;
6. завершает работу.

### Официанты

Количество потоков равно `waiters`.

Официант:

1. ожидает посетителя;
2. принимает его заказ;
3. передает заказ координатору кухни;
4. ожидает сборки именно этого заказа;
5. выдает его тому же посетителю;
6. переходит к следующему посетителю.

### Повара

Количество потоков равно `cooks`.

Повар:

1. ожидает доступную операцию;
2. извлекает ее из кухонной очереди;
3. захватывает семафор нужного оборудования;
4. выполняет операцию заданное время;
5. освобождает оборудование;
6. разблокирует следующую операцию блюда либо передает готовое блюдо.

### Координатор кухни

Один отдельный поток:

- принимает переданные официантами заказы;
- проверяет их выполнимость;
- создает блюда и операции;
- помещает доступные операции в кухонную очередь;
- обрабатывает готовые блюда;
- собирает заказ после готовности всех его блюд;
- будит нужного официанта.

## Синхронизация

### Мьютексы

`state_mutex` защищает общие изменяемые структуры ресторана:

- состояния заказов;
- операции;
- кухонную очередь;
- зону готовых блюд;
- статистику.

У логгера есть отдельный мьютекс, поэтому сообщения разных потоков не
перемешиваются внутри одной строки.

### Семафоры

Используются безымянные POSIX-семафоры `sem_t`.

| Семафор | Назначение |
|---|---|
| `visitor_waiting` | число посетителей, ожидающих официанта |
| `coordinator_events` | события для координатора |
| `kitchen_items` | число операций в кухонной очереди |
| `kitchen_slots` | свободные места в кухонной очереди |
| `ready_slots` | свободные места в зоне готовых блюд |
| `equipment[]` | свободные единицы каждого типа оборудования |
| `order_ready[]` | индивидуальное ожидание официантом готовности заказа |
| `visitor_done[]` | индивидуальное ожидание посетителем результата заказа |
| `visitor_finished` | завершившиеся потоки посетителей |

Если вместимость очереди в конфигурации равна `0`, она считается
неограниченной в пределах максимального размера модели.

---

## Почему не возникает одновременного использования оборудования

Для каждого типа оборудования создается считающий семафор с начальным
значением, равным числу его единиц.

Перед началом операции повар выполняет захват семафора. Если все единицы
заняты, поток повара блокируется. После окончания операции семафор
увеличивается обратно.

Поэтому одновременно работающих операций данного типа не может быть больше,
чем физически заданных единиц оборудования.

---

## Зависимости операций

При создании блюда доступной становится только его первая операция.

После завершения операции повар под защитой `state_mutex` увеличивает счетчик
выполненных шагов. Только после этого следующая операция переводится в
состояние `OP_READY`, а координатор может поставить ее в очередь.

Таким образом, второй шаг блюда не может стартовать до завершения первого.

## Ограниченная кухонная очередь

Вместимость задается:

```text
kitchen_queue_capacity=N
```

Свободные места учитывает `kitchen_slots`.

Координатор использует неблокирующую попытку `sem_trywait()`. Если очередь
заполнена, операция остается в состоянии ожидания и не теряется. После того
как повар извлекает элемент, он возвращает слот и будит координатора.

Это решение также не позволяет координатору зависнуть на заполненной кухонной
очереди и перестать обрабатывать другие события.

---

## Зона готовых блюд

Вместимость задается:

```text
ready_queue_capacity=N
```

После завершения последней операции блюда повар сначала освобождает рабочее
оборудование, а затем получает слот `ready_slots`.

Это важно: поток не удерживает плиту, печь, гриль или стол во время ожидания
места в зоне готовых блюд.

Координатор забирает блюдо из зоны и сразу возвращает слот.

---

## FIFO и LIFO

```text
priority=fifo
```

или:

```text
priority=lifo
```

Правило применяется к выбору операций кухонной очереди.

- `FIFO` — сначала более ранняя операция;
- `LIFO` — сначала более поздняя операция.

## Завершение по Ctrl+C

Пример долгого запуска:

```bash
./build/restaurant \
  --config configs/random_orders.conf \
  --visitors 20 \
  --unit-ms 300
```

Нажать:

```text
Ctrl+C
```

Обработчик сигнала выполняет только безопасное действие — записывает номер
сигнала в `volatile sig_atomic_t`.

Рабочие потоки периодически проверяют условие остановки. После прерывания
основной код:

1. устанавливает общий флаг завершения;
2. будит потоки, ожидающие на семафорах;
3. выполняет `pthread_join`;
4. печатает статистику;
5. закрывает журнал.

Для `SIGINT` программа возвращает код `130`.

Проверка:

```bash
echo $?
```

## Формат конфигурации

Пример:

```text
visitors=4
waiters=2
cooks=3
arrival_interval=2
kitchen_queue_capacity=4
ready_queue_capacity=2
priority=fifo
seed=42

equipment_stove=1
equipment_oven=1
equipment_grill=1
equipment_table=2

dish=Soup|stove:3,table:1
dish=Roast|oven:4,table:1
dish=Grilled fish|grill:3,table:2

order=Soup,Roast
order=Roast,Grilled fish
order=Grilled fish,Soup
order=Soup,Roast
```

Описание блюда:

```text
dish=Название|оборудование:время,оборудование:время,...
```

Если `order=` отсутствуют, состав заказов генерируется по `seed`.
