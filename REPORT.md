# 1. Постановка задачи

Требовалось разработать консольное приложение для Linux на языке C,
моделирующее работу кухни ресторана с использованием многопоточности.

В ресторан приходят посетители и формируют заказы из одного или нескольких
блюд. Официант принимает заказ и передает его на кухню. Каждое блюдо состоит
из последовательности операций, для выполнения каждой из которых необходимы
повар и определенный тип оборудования: плита, печь, гриль или рабочий стол.

Повара выбирают доступные операции из общей очереди. Одна единица оборудования
одновременно используется не более чем одним поваром. Следующая операция блюда
может начаться только после завершения предыдущей.

Готовые блюда собираются по номеру заказа. Официант выдает заказ только после
готовности всех входящих в него блюд и только тому посетителю, которому этот
заказ принадлежит.

Вместимость кухонной очереди и зоны готовых блюд может быть ограничена.

# 3. Общая архитектура

Программа представляет один процесс Linux, внутри которого создается множество
POSIX-потоков.

Состав потоков:

| Сущность | Количество потоков |
|---|---:|
| Посетитель | `visitor_count` |
| Официант | `waiter_count` |
| Повар | `cook_count` |
| Координатор кухни | 1 |
| Главный поток | 1 |

Главный поток отвечает за чтение конфигурации, установку обработчиков сигналов,
создание модели, запуск потоков, ожидание завершения посетителей, остановку
рабочих потоков и вывод итоговой статистики.

# 5. Отображение сущностей предметной области на потоки

## 5.1. Посетители

Каждый посетитель реализован отдельным потоком.

Его сценарий:

1. поток ожидает заданного времени появления;
2. посетитель приходит в ресторан;
3. его заказ становится доступен официантам;
4. поток блокируется в ожидании результата;
5. после доставки либо отмены заказа посетитель покидает ресторан;
6. поток завершается.

Для индивидуального ожидания результата используется отдельный семафор
`visitor_done[i]`.

---

## 5.2. Официанты

Каждый официант является отдельным рабочим потоком.

Официант ожидает семафор `visitor_waiting`. После пробуждения он под защитой
общего мьютекса выбирает посетителя, ожидающего обслуживания.

После принятия заказа официант:

1. закрепляет заказ за собой;
2. передает его координатору;
3. ожидает индивидуальный семафор `order_ready[order]`;
4. после сборки заказа выдает его владельцу;
5. возвращается к ожиданию следующего посетителя.

В данной модели один официант одновременно ведет не более одного активного
заказа.

---

## 5.3. Повара

Каждый повар выполняется в отдельном потоке.

Повар блокируется на семафоре `kitchen_items`, который показывает количество
операций в кухонной очереди.

После получения задания повар:

1. извлекает операцию согласно правилу FIFO/LIFO;
2. освобождает один слот кухонной очереди;
3. захватывает семафор нужного оборудования;
4. начинает приготовление;
5. ожидает время операции;
6. освобождает оборудование;
7. помечает операцию завершенной;
8. либо делает доступной следующую операцию блюда, либо передает готовое блюдо
   в зону готовых блюд.

---

## 5.4. Координатор кухни

Координатор кухни представлен отдельным потоком.

Он выполняет роль управляющего участника:

- принимает новые заказы от официантов;
- проверяет наличие оборудования;
- явно отменяет невыполнимые заказы;
- создает структуры блюд и операций;
- переводит первые операции блюд в состояние готовности;
- заполняет кухонную очередь;
- обрабатывает блюда из зоны готовых;
- собирает заказ после получения всех его блюд;
- сигнализирует соответствующему официанту.

Для пробуждения координатора используется семафор `coordinator_events`.

---

# 6. Модель общей памяти

Все потоки одного процесса имеют общее адресное пространство, поэтому основные
структуры модели доступны одновременно нескольким участникам.

К общим изменяемым данным относятся:

- состояния заказов;
- состояния операций;
- кухонная очередь;
- зона готовых блюд;
- счетчики готовности;
- статистика.

Эти данные защищаются мьютексом:

```c
pthread_mutex_t state_mutex;
```

Любое изменение согласованного состояния выполняется внутри критической
секции.

---

# 7. Семафоры

В программе используются безымянные POSIX-семафоры, созданные через
`sem_init()`.

## 7.1. Посетители и официанты

```text
visitor_waiting
```

Значение показывает число посетителей, заявки которых еще не забраны
официантами.

Посетитель выполняет `sem_post()`, официант — `sem_wait()`.

---

## 7.2. Кухонная очередь

Используются два семафора:

```text
kitchen_items
kitchen_slots
```

`kitchen_items` показывает число операций, находящихся в очереди.

`kitchen_slots` показывает количество свободных мест и тем самым реализует
ограниченную вместимость.

Если в конфигурации вместимость равна нулю, очередь считается практически
неограниченной в пределах максимально допустимого числа операций модели.

---

## 7.3. Оборудование

Для каждого типа оборудования имеется отдельный считающий семафор:

```text
equipment[stove]
equipment[oven]
equipment[grill]
equipment[table]
```

Начальное значение равно количеству единиц оборудования.

Например, при одной плите значение семафора `stove` равно 1. Первый повар
уменьшает его до 0. Все остальные повара, которым требуется плита, должны
ожидать. После завершения операции повар выполняет `sem_post()`.

---

## 7.4. Зона готовых блюд

Свободные места учитываются семафором:

```text
ready_slots
```

После завершения блюда повар сначала освобождает оборудование и только затем
пытается получить место в ready-area.

Таким образом, ожидание заполненной зоны готовых блюд не удерживает плиту,
печь, гриль или рабочий стол.

---

## 7.5. Индивидуальные события

Для каждого заказа и посетителя создаются отдельные семафоры:

```text
order_ready[i]
visitor_done[i]
```

Это позволяет разбудить именно нужного официанта и именно нужного посетителя,
не используя активное ожидание.

---

# 8. Потокобезопасный вывод

Одновременный `printf()` из большого количества потоков может приводить к
перемешиванию сообщений.

Поэтому `Logger` содержит отдельный `pthread_mutex_t`.

Формирование и запись целой строки выполняются внутри одной критической
секции. В результате наблюдатель получает последовательный журнал событий,
хотя события инициируются разными потоками.

Запись в файл реализована через файловый дескриптор и системные интерфейсы:

```c
open()
write()
close()
```

---

# 9. Время моделирования

Во второй работе операции действительно выполняются асинхронно, поэтому
длительность используется как реальное ожидание потока.

Чтобы не ждать секунды или минуты при тестировании, введен масштаб:

```text
--unit-ms N
```

Одна модельная единица соответствует `N` реальным миллисекундам.

Например:

```bash
--unit-ms 100
```

означает, что операция длительностью 4 выполняется примерно 400 мс.

Для тестов используется малое значение, например `2`, а для демонстрации на
защите удобно использовать 100–200 мс.

---

# 10. Создание операций и зависимости

После принятия заказа координатор создает все операции его блюд.

Для каждого блюда только первая операция получает состояние `OP_READY`.
Остальные находятся в `OP_NOT_READY`.

После завершения операции повар под защитой `state_mutex` увеличивает число
выполненных шагов блюда. Если блюдо еще не закончено, следующая операция
переводится в `OP_READY` и координатор получает событие.

Следовательно, зависимая операция физически не может попасть в кухонную очередь
раньше завершения предыдущей.

---

# 11. Кухонная очередь и отсутствие взаимной блокировки

Наивная реализация могла бы заставить координатора выполнять блокирующий
`sem_wait(kitchen_slots)`. Это опасно: при полностью занятой очереди координатор
мог бы перестать обрабатывать остальные события.

В реализации используется `sem_trywait()`.

Если места нет:

- операция остается `OP_READY`;
- выводится событие о заполненной очереди;
- координатор продолжает работу.

Когда повар извлекает операцию, он:

1. выполняет `sem_post(kitchen_slots)`;
2. будит координатора;
3. координатор повторяет попытку постановки ожидающей операции.

Так операция не теряется, а координатор не удерживается заполненной очередью.

---

# 12. FIFO и LIFO

В конфигурации доступны:

```text
priority=fifo
priority=lifo
```

В режиме FIFO повар извлекает более раннюю операцию.

В режиме LIFO выбирается последняя поставленная операция.

При освобождении места координатор также учитывает последовательность появления
операций, ожидающих постановки.

---

# 13. Проверка инвариантов

## 13.1. Одну единицу оборудования использует не более одного повара

Гарантируется считающим семафором оборудования.

Если единица одна, после первого успешного `sem_wait()` значение становится
нулевым, и другой поток не может продолжить до `sem_post()`.

---

## 13.2. Повар выполняет не более одной операции

Каждый повар — один последовательный поток. Он не запрашивает новое задание,
пока текущая операция не завершена.

---

## 13.3. Зависимая операция не начинается раньше предыдущей

Следующий шаг переводится из `OP_NOT_READY` в `OP_READY` только после
завершения текущего шага.

---

## 13.4. Блюдо готово только после всех операций

В `RuntimeDish` хранится число завершенных операций. Блюдо объявляется готовым,
когда оно становится равно общему числу операций блюда.

---

## 13.5. Заказ выдается только после готовности всех блюд

Координатор увеличивает `ready_dishes` конкретного заказа при получении блюда из
ready-area. Только при равенстве `ready_dishes == dish_count` заказ переводится
в состояние `ORDER_ASSEMBLED`.

После этого разблокируется официант данного заказа.

---

## 13.6. Заказ выдается своему посетителю

Индекс заказа совпадает с индексом владельца-посетителя. Для каждого заказа
существуют индивидуальные семафоры готовности, поэтому сигнал не может быть
случайно принят официантом другого заказа.

---

# 14. Невыполнимые заказы

При поступлении заказа координатор проверяет все требуемые типы оборудования.

Если блюдо требует оборудование, количество которого равно нулю, заказ
помечается `ORDER_CANCELED`.

Пример:

```text
equipment_oven=0
```

и блюдо:

```text
dish=Roast|oven:3,table:1
```

Такой заказ отменяется явно. Поток посетителя и поток официанта получают
соответствующие сигналы и корректно завершают данный сценарий.

# 17. Обработка сигналов

Обрабатываются:

```text
SIGINT
SIGTERM
```

В обработчике сигнала не вызываются функции логирования, освобождения памяти или
pthread. Он только записывает номер сигнала в переменную типа
`volatile sig_atomic_t`.

Рабочие потоки используют ожидания с тайм-аутом и периодически проверяют
условие остановки.

После получения сигнала основной код:

1. устанавливает общий атомарный флаг `shutdown`;
2. будит потоки, ожидающие работы;
3. дожидается их через `pthread_join()`;
4. выводит частичную статистику;
5. закрывает журнал и освобождает память.

При `SIGINT` возвращается код 130.

---

# 18. Завершение при нормальных входных данных

Основной поток ожидает семафор `visitor_finished` столько раз, сколько создано
посетителей.

Посетитель увеличивает его только после того, как заказ был доставлен либо
явно отменен.

Поэтому нормальное завершение означает, что все запланированные посетители
получили конечный результат.

После этого устанавливается `shutdown`, рабочие потоки пробуждаются и
объединяются с главным через `pthread_join()`.

Для семафоров:

# 28. Проверка Ctrl+C

Для теста запускалась команда с увеличенным числом автоматически формируемых
заказов, после чего процесс получал `SIGINT`.

Получено:

```text
Interrupt received; restaurant is stopping safely
Termination: interrupted
```

Код возврата:

```text
130
```

При этом рабочие потоки завершаются через общий механизм остановки, а главный
поток выполняет `pthread_join()`.

# 29. Возможные особенности многопоточного вывода

Порядок независимых событий между запусками может меняться.

Например, два повара, которые одновременно получили разные виды оборудования,
могут вывести сообщения в разной последовательности.

Это является нормальным следствием асинхронного планирования потоков и не
нарушает инварианты модели.

При этом каждая отдельная строка журнала остается целой благодаря мьютексу
логгера.

# 30. Отличия от первой работы

В первом задании параллельность предметной области имитировалась одним
последовательным циклом и модельным временем.

Во втором задании:

- участники стали настоящими POSIX-потоками;
- несколько операций реально могут выполняться одновременно;
- ограничение оборудования реализовано семафорами;
- очереди являются точками синхронизации;
- требуется защита общей памяти мьютексом;
- появляется недетерминированный порядок независимых событий;
- завершение требует корректной остановки и `pthread_join()` всех потоков.

Формат входных конфигураций при этом сохранен, поэтому одинаковые предметные
сценарии можно сравнивать между двумя заданиями.

# 31. Ограничения и принятые решения

1. Один официант ведет один активный заказ до его выдачи.
2. Действия координатора считаются мгновенными относительно времени
   приготовления.
3. Все операции внутри одного блюда строго последовательны.
4. Приоритет FIFO/LIFO применяется к кухонным операциям.
5. Состав случайных заказов вычисляется воспроизводимо до запуска рабочих
   потоков, чтобы планировщик ОС не влиял на генератор случайных чисел.
6. Масштаб `--unit-ms` влияет только на реальную скорость демонстрации, но не
   изменяет заданные относительные длительности операций.

# 32. Вывод

В результате разработано многопоточное консольное приложение на языке C для
Linux, моделирующее работу кухни ресторана.

Все основные поведенческие сущности варианта представлены отдельными потоками:
посетители, официанты, повара и координатор кухни.

Для согласованного взаимодействия применяются POSIX-мьютексы и семафоры.
Семафоры используются для очередей, индивидуальных событий и ограничения
доступа к оборудованию. Общая память защищена мьютексом.

Программа поддерживает ограниченные очереди, FIFO/LIFO, отмену невыполнимых
заказов, журналирование, сигналы, корректное завершение, статистику и
автоматические тесты.

Подготовленные сценарии завершаются корректно, а проверки санитайзерами не
выявили ошибок памяти, неопределенного поведения или гонок данных в
проверенном сценарии.
